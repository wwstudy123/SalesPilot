# SAGT 零售销售智能体系统 需求文档（PRD）

> 版本：v1.2 ｜ 项目代号：ShopPilot ｜ 模块命名：SAGT（Sales Agent）
> 定位：零售行业销售智能体系统。通过智能分析客户信息，协助员工更好地维护客户关系，提升销售效率和客户服务质量。
> 核心职责：基于客户数据分析，为员工提供智能化的客户关系维护支持。
>
> 已拍板决策（贯穿全文）：
> 1. AI 与员工的关系为 **Copilot（提议-采纳制）**：标签/日程/画像字段均为"AI 提议、员工采纳生效"，采纳率与修正率作为核心评测指标；
> 2. 客户数据全部为 **Mock 种子数据**（20 客户 × 人均 15 条跟进记录 × 若干消费/客服记录），外部生态（微信会话、微信小店）以 Mock CRM 服务模拟，接口按真实集成形状设计；
> 3. 保留**员工对话工作台**作为主入口，承载自然语言交互、场景菜单与中断确认。
>
> 全局约束：不接入任何真实外部系统；一切写操作走人工在环；AI 回答必须可解释（附依据/引用），无依据宁可拒答。
>
> v1.1 变更（对齐评审结论）：补充新客冷启动引导、客户移交规则、跨客户注入防护、员工级配额、同字段提案合并；削减 mem_user（员工偏好）至 ADV、功能授权简化为角色级、客服建议菜单合并、批量标签重算挪 ADV、Rerank 默认 LLM listwise。
> v1.2 变更（简历对齐裁决）：意图表 +knowledge_qa（13 个，不加 quote_query/product_recommend）；RAG chunk 元数据加 domain 分域过滤；评测体系升级为 500 条测试集基线 + 四维 Judge + 工程目标值；报价域不建，简历措辞改为"消费记录查询"。

## 1. 项目概述

### 1.1 背景
零售门店/私域销售场景中，员工的客户关系维护高度依赖个人经验：跟进记录散落在对话里无人整理、客户画像在员工脑中而非系统中、回访时机靠记忆、新人上手慢且话术质量不稳定。客户资产随员工流失而流失。

### 1.2 产品定位
面向销售员工的 **AI Copilot**：不替代员工与客户对话，而是让每个普通员工拥有 Top Sales 的判断力——自动沉淀客户画像、自动识别跟进信号、按场景给出带依据的话术建议、自动安排维护日程。

### 1.3 核心价值主张
| 角色 | 价值 |
|---|---|
| 员工 | 打开客户即见画像与建议，跟进不漏、话术不慌 |
| 管理者 | 客户资产机构化沉淀，服务质量可量化（采纳率/修正率） |
| 组织 | 客户关系从"员工私有"变为"组织资产" |

### 1.4 产品目标（可度量）
| 目标 | 口径 |
|---|---|
| 画像自动化 | 种子客户画像字段覆盖率 ≥ 90%（对标人工标注集） |
| 标签质量 | 标签人工修正率 ≤ 15% |
| 建议有用性 | 话术建议采纳率 ≥ 50%（员工行为数据） |
| 信号识别 | 跟进信号（承诺/异议/兴趣/流失风险）召回率 ≥ 85% |
| 意图路由 | 三路融合 L1 准确率 ≥92%（500 条评测集） |
| 全程可观测 | 100% 请求产生完整 Run/Span 追踪 |

### 1.5 明确不做（Non-Goals）
真实微信接入、真实支付/订单系统、多租户 SaaS、员工端 App、客户直接对话的聊天机器人（本项目是 Copilot，客户不是系统用户）。

## 3. 用户故事

**员工**
- US-E1 作为员工，我打开客户详情就能看到 AI 提取的画像（偏好/需求/价值分层）和每条结论的依据，以便拜访前 30 秒进入状态。
- US-E2 作为员工，我说"帮我给王女士写个回访话术"，能拿到基于她的画像和历史、带话术库引用的草稿，并可要求重新生成。
- US-E3 作为员工，AI 发现客户说过"下周看新款"，能自动给我一条日程建议，我确认后进入我的待办。
- US-E4 作为员工，AI 打的标签我能看到理由，点一下就能修正，且修正后不再重复犯错。
- US-E5 作为员工，我能问"和张总情况类似的客户，上次是怎么成交的"，得到相似客户案例参考。
- US-E6 作为员工，每次 AI 建议我都能在监控里看到它是怎么得出的。

**管理者**
- US-M1 作为管理者，我要看到每个员工的客户池、关系状态分布与跟进活跃度。
- US-M2 作为管理者，我要看到建议采纳率、标签修正率、画像覆盖率三张质量报表。
- US-M3 作为管理者，我要管理员工授权（哪个员工可用哪些功能、负责哪些客户）。

## 4. 信息架构

```
SAGT
├── sagt_sidebar（员工端）
│   ├── 对话工作台          # 自然语言交互 + 场景菜单 + 流式响应 + 中断确认
│   ├── 我的客户            # 客户列表（按标签/阶段/下次跟进筛选）
│   ├── 客户详情            # 画像 / 标签 / 跟进时间线 / 消费记录 / 建议入口 / 首访采集清单（新客）
│   └── 我的日程            # AI 建议日程 + 自有待办（确认/改期/完成）
└── sagt_admin（管理端）
    ├── 概览                # 客户资产/采纳率/修正率/画像覆盖率
    ├── 员工管理            # 授权、客户分配
    ├── 客户管理            # 全量客户档案、画像与关系状态
    ├── 会话监控            # 员工与 AI 的会话记录、建议采纳明细
    ├── 服务记录            # 客服交互记录与服务质量摘要
    ├── 订单管理            # 微信小店订单（Mock）与购买行为
    ├── Agent Monitor       # Run/Span 瀑布图、概览
    └── 评测中心            # 数据集、评测任务、报告对比
```

## 5. 核心功能模块（系统视角：SAGT 四模块）

| 模块 | 形态 | 核心职责 |
|---|---|---|
| **sagt_agent** | Python 3.11 + FastAPI + LangGraph 服务 | 核心智能分析引擎：4 Agent 编排、意图分类、MCP 调用、RAG、分层记忆、Monitor/Eval |
| **sagt_admin** | React SPA | 管理与监控界面（§4 右半） |
| **sagt_sidebar** | React SPA（与 admin 同前端仓库双入口） | 员工交互界面：对话、场景菜单、流式响应、中断确认 |
| **sagt_client** | OpenAPI 契约 + Python SDK 包（演示期不独立成服务） | 对外标准化访问接口：数据读写、记忆维护；未来对接真实微信生态时升格为独立服务。真实接入点即**会话记录同步**（微信聊天记录落为跟进记录），演示期以员工手工录入替代（数据来源叙事） |
| business-mock（Java 21 + Spring Boot） | 支撑服务 | Mock CRM：员工/客户/跟进/消费/客服/订单数据与业务规则，业务事实唯一写入口 |
| mcp-server | Python 服务 | 统一工具层，封装 business-mock REST 供 sagt_agent 调用 |

## 6. 功能卡片

> 每张卡片十字段：功能目的 / 输入 / 处理逻辑 / 输出 / 异常情况 / 权限 / Agent / MCP / RAG / Memory。
> 阶段标记：【MVP】【P2】【ADV】。

### 6.1 对话工作台【MVP】（sagt_sidebar）
| 字段 | 内容 |
|---|---|
| 功能目的 | 员工与智能体自然语言交互的主入口；场景菜单免分类直达；承载流式响应与中断确认 |
| 输入 | 员工文本指令；场景菜单点击（画像分析/标签建议/聊天建议/异议求助/日程建议）；对建议的采纳/修改/拒绝/重新生成 |
| 处理逻辑 | 菜单指令以固定意图注入（routing_type=menu）；自然语言走三路意图分类 → Orchestrator 路由 → 领域 Agent 执行 → SSE 流式返回；write 操作产出 proposal 触发中断确认界面（确认/放弃/重新生成） |
| 输出 | 流式回答（带依据引用）、建议卡片（采纳状态）、中断确认面板、会话历史 |
| 异常情况 | SSE 断线自动重连补齐；LLM 超时降级话术并标记 Run；详见 §17 |
| 权限 | employee；只能操作自己负责的客户 |
| Agent / MCP / RAG / Memory | 是 / 是 / 是 / 是 |

### 6.2 客户画像提取【MVP】（Profile Agent）
| 字段 | 内容 |
|---|---|
| 功能目的 | 把散落的跟进/消费记录沉淀为结构化客户 Profile：偏好、需求、价值分层、敏感点、关系阶段 |
| 输入 | 触发：新跟进记录落库（事件驱动增量）/ 员工手动"重新分析" / 打开客户详情时缓存缺失 |
| 处理逻辑 | Profile Agent 读取该客户全部跟进+消费记录 → LLM 结构化抽取（JSON Schema 约束）→ 与既有画像做字段级 diff → 产出"画像更新提案"（变更字段+依据记录 ID）→ 员工采纳后写入 |
| 输出 | 画像卡片：偏好/需求/价值分层(高/中/低)/生命周期阶段/敏感点/最近关注点，每字段附依据引用与更新时间 |
| 异常情况 | 记录不足（<3 条）不呈现空白态，改出"首访信息采集清单"（冷启动引导：该问什么）；字段冲突（新旧矛盾）双值并呈由员工裁决；抽取失败不覆盖旧画像；同字段已有未处理提案时，新抽取结果合并进原提案而非新增 |
| 权限 | employee（自己客户）；manager 可查全量 |
| Agent / MCP / RAG / Memory | 是（Profile）/ 是（list_follow_ups、list_purchases、update_profile_field）/ 否 / **是（写入方：画像即长期记忆）** |

### 6.3 自动标签标注【MVP】（Ops Agent）
| 字段 | 内容 |
|---|---|
| 功能目的 | 为客户自动打标（生命周期阶段/偏好类/风险类），支撑筛选、装配技能与日程优先级 |
| 输入 | 触发：画像更新后联动 / 批量重算【ADV】（管理者发起）/ 员工手动"重新打标" |
| 处理逻辑 | Ops Agent 基于画像+近期跟进 → 按标签体系（预定义字典，含判定规则描述）产出建议标签集，每个标签附依据（引用具体跟进记录或画像字段）→ save_tags 提案 → 员工确认生效；员工修正记录回流评测 |
| 输出 | 标签建议卡（标签名/类型/依据/置信度）；生效后进入客户档案与筛选器 |
| 异常情况 | 低置信标签（<0.6）默认折叠为"待确认"；与既有标签冲突时标注"替换建议"而非静默覆盖 |
| 权限 | employee 确认自己客户；manager 发起批量【ADV】 |
| Agent / MCP / RAG / Memory | 是（Ops）/ 是（get_customer_profile、list_follow_ups、save_tags）/ playbook_kb（标签判定规则）/ 读画像 |

### 6.4 智能聊天建议【MVP】（Coach Agent）
| 字段 | 内容 |
|---|---|
| 功能目的 | 按场景生成个性化沟通建议与话术草稿：回访、促单、异议处理、挽回等 |
| 输入 | 员工指令（"给王女士写回访话术，重点是新款到货"）或客户详情页菜单入口；可选附加要求 |
| 处理逻辑 | Coach Agent 装配生命周期技能 → 读画像+近 3 次跟进 → 检索 playbook_kb（场景话术/异议处理）+ product_kb（涉及产品时）→ 相似客户检索（可选，Milvus 画像向量）→ 生成草稿，强制引用依据 |
| 输出 | 建议卡：沟通要点 + 话术草稿 + 依据区（引用了哪条记录/哪段话术/哪个画像字段）；操作：采纳（可先编辑）/重新生成（附要求，≤2 次）/拒绝（必填一句话原因，回流评测） |
| 异常情况 | 与已知事实冲突的表述（如把已购当新客推销）在生成后自检拦截重写；无相关话术库内容时明确标注"通用建议"，不冒充库内话术 |
| 权限 | employee（自己客户） |
| Agent / MCP / RAG / Memory | 是（Coach，可含 Orchestrator 编排的相似客户子任务）/ 是（get_customer_profile、list_purchases、search_similar_customers）/ 是（playbook_kb+product_kb）/ 读画像+偏好 |

### 6.5 智能日程管理【P2】（Ops Agent 信号识别子任务）
| 字段 | 内容 |
|---|---|
| 功能目的 | 从交流内容中识别跟进信号，自动生成日程/提醒建议，防止跟进遗漏 |
| 输入 | 触发：新跟进记录落库（增量扫描）/ 每日批量巡检 / 员工指令"看看我最近有什么要跟进的" |
| 处理逻辑 | 信号分类：承诺类（"下周看新款"）/异议未决类（"价格再考虑"）/兴趣类/流失风险类（>30 天未互动+负向信号）→ 结合画像价值分层定优先级与建议时间 → create_schedule 提案 → 员工确认/改期/放弃 |
| 输出 | 日程建议卡（客户/事由/建议时间/优先级/来源记录引用）；确认后进入"我的日程" |
| 异常情况 | 同一信号不重复生成（去重键=客户+信号类型+来源记录）；放弃原因记录回流评测 |
| 权限 | employee（自己日程） |
| Agent / MCP / RAG / Memory | 是 / 是（list_follow_ups、create_schedule、list_schedules）/ 否 / 读画像价值分层 |

### 6.6 相似客户检索【ADV】（Coach Agent 子能力）
| 字段 | 内容 |
|---|---|
| 功能目的 | "和张总类似的客户怎么成交的"——把个体经验变成可复用的组织经验 |
| 输入 | 目标客户 + 问题 |
| 处理逻辑 | 画像向量化 → Milvus 检索 top-N 相似客户 → 过滤已成交/活跃案例 → LLM 提炼可借鉴动作 |
| 输出 | 相似案例卡（客户脱敏摘要 + 相似维度 + 历史有效动作） |
| 异常情况 | 相似度过低（<阈值）直接说明"暂无可参考案例"，不硬凑 |
| 权限 | employee（案例脱敏展示） |
| Agent / MCP / RAG / Memory | 是 / 是（search_similar_customers）/ 否 / **Milvus 画像向量是本体** |

### 6.10 Agent Monitor【MVP 简 / P2 全】
| 字段 | 内容 |
|---|---|
| 功能目的 | 全链路可观测：每条建议可回放决策过程（意图→画像读取→检索→生成→提案） |
| 输入 | Run 筛选（Agent/意图/状态/耗时）；Run 详情 |
| 处理逻辑 | Run→Span 树落库（router/agent/llm_call/tool_call/rag_retrieval/memory_op/skill_attach/proposal）；瀑布时间线展示输入输出摘要、tokens、耗时、成本 |
| 输出 | Run 列表、瀑布图、概览看板（意图分布/工具成功率/p50/p95/日成本） |
| 异常情况 | 超长 payload 截断；孤儿 Span 标红不丢弃 |
| 权限 | manager；访客只读；employee 仅可见自己会话的 Run |
| Agent / MCP / RAG / Memory | 记录对象含四者，功能本身不调用 |

### 6.11 评测中心【P2 CLI / ADV 平台】
| 字段 | 内容 |
|---|---|
| 功能目的 | 用数据集量化 AI 质量并回归对比；员工行为信号（采纳/修正/拒绝）自动沉淀为新评测样本 |
| 输入 | 数据集（profile_eval / tag_eval / signal_eval / talk_eval / e2e_task_eval）、基线、预算 |
| 处理逻辑 | eval_mode 复用线上链路（不写业务库，脚本模拟触发事件）；指标见 §16；报告与基线逐 case diff |
| 输出 | 评测报告、回归 diff、基线更新 |
| 异常情况 | 预算超限提前终止；Judge 不可用维度标 N/A |
| 权限 | manager |
| Agent / MCP / RAG / Memory | 评测对象即全链路；eval_mode 禁写记忆 |

### 6.12 人工在环中断确认（HITL 通用机制）【MVP】
| 字段 | 内容 |
|---|---|
| 功能目的 | 一切 write 操作的统一闸门：AI 只提议，生效必须经员工确认 |
| 输入 | 提案（类型：画像字段/标签/日程/话术采纳）；操作：确认 / 放弃 / 重新生成 |
| 处理逻辑 | write 工具返回 proposal（LangGraph interrupt，Run=waiting_approval）→ sidebar 渲染确认面板 → 确认携 approval_token 回调执行；放弃置 rejected；重新生成携员工反馈重跑该节点（建议类任务允许 ≤2 次）；30 分钟未处理过期 |
| 输出 | 确认面板、执行回执、行为日志（自动进评测信号池） |
| 异常情况 | 过期提案灰显"已过期"；无凭证 write 被 MCP Server 拒绝并记安全事件 |
| 权限 | employee（自己客户/日程） |
| Agent / MCP / RAG / Memory | 是 / 是 / 否 / 否 |

## 7. 核心业务流程

**F1 画像沉淀（事件驱动，MVP）**
新跟进记录落库 → Profile Agent 增量抽取 → 字段级 diff 产出更新提案 → 员工采纳 → 画像落库 + 向量更新（Milvus）→ 联动触发标签复核。

**F2 话术生成（MVP，核心演示链路）**
员工指令/菜单 → 意图路由 → Coach Agent 装配生命周期技能 → 读画像+跟进 → 检索 playbook_kb/product_kb →（可选）相似客户案例 → 生成带依据草稿 → 员工采纳/修改/重新生成 → 行为日志入评测池。

**F3 信号识别与日程（P2）**
跟进记录落库 → Ops Agent 信号分类（承诺/异议/兴趣/流失风险）→ 结合价值分层定优先级 → 日程提案 → 员工确认进入待办 → 完成后回写跟进闭环。

**F4 拜访准备组合任务（P2，编排演示）**
"帮我准备明天拜访王女士" → Orchestrator DAG：画像调取 → 话术草稿 → 日程/待办检查 → 聚合为"拜访准备包"单卡输出。

**F5 标签批量治理（ADV）**
管理者发起批量重算 → Ops Agent 逐客户产出建议 → 员工分批确认 → 修正率报表更新。

**F6 知识入库（MVP）**
上传话术/产品文档 → 解析切片向量化 → active 版本原子切换 → 检索测试验证 → 建议即时引用新内容。

## 8. AI 对话流程

### 8.1 单轮请求生命周期
```
员工消息/菜单 → 会话上下文装载(Redis) → 客户上下文注入(当前选中客户)
→ 意图分类(menu 直达 / Rule+Embedding+LLM 三路融合)
→ Orchestrator 路由 {primary_agent, secondary, reason, confidence}
→ Agent 装配 Skills → [画像读取 / MCP 工具 / RAG 检索]*
→ write 操作? → proposal + LangGraph interrupt → 中断确认面板
→ SSE 流式输出 → 消息落库 → Trace 收尾 → 行为信号记录
```

### 8.2 SSE 事件协议
| 事件 | 用途 |
|---|---|
| intent / agent_switch | 展示路由结果与转交 |
| tool_call | "正在读取王女士的跟进记录…" |
| rag_citation | 依据角标 |
| token | 流式文本 |
| proposal | 渲染建议卡/中断确认面板 |
| clarify / error / done | 澄清、异常、结束 |

### 8.3 关键规则
- 员工必须处于"某客户上下文"中发起客户相关指令，否则先澄清目标客户；客户上下文槽位**锁定当前客户**，对话中涉及其他客户的请求一律澄清/拒绝（防跨客户提示词注入，MCP 归属校验兜底）；
- 澄清/低置信（0.4~0.7）给候选；<0.4 兜底并记 unknown 入评测池;
- 建议类任务允许重新生成 ≤2 次，超限提示员工手动编辑；
- eval_mode：不写业务库、不写记忆、行为信号不入池。

## 10. Agent 路由规则

4 Agent 架构（Supervisor 中枢，领域 Agent 不互相直连）：

| Agent | 职责 | 工具 | RAG |
|---|---|---|---|
| Orchestrator | 路由、澄清、组合任务 DAG、聚合、HITL 闸门、fallback 控制 | search_customers、批量任务调度 | 不用 |
| Profile Agent | 画像提取与增量更新 | list_follow_ups、list_purchases、update_profile_field(write) | 不用 |
| Coach Agent | 话术/沟通/异议建议、相似客户 | get_customer_profile、list_purchases、search_similar_customers | playbook_kb + product_kb |
| Ops Agent | 标签、信号识别、日程 | get_customer_profile、list_follow_ups、save_tags(write)、create_schedule(write)、list_schedules | playbook_kb（标签规则） |

路由规则沿用冻结版 R1~R8：粘滞优先（中断确认未完成的提案优先恢复）、置信度分级、技能按客户标签装配、工具白名单技能只收窄、全决策留痕。

预算：每 Run ≤5 次 Agent 调用；单任务 LLM ≤4 轮、工具 ≤6 次；每 Run 工具总数 ≤15；重新生成 ≤2 次。员工级配额：每人每日建议生成次数上限（Redis 计数），超限提示稍后再试，防止连点重新生成导致成本失控。

## 11. MCP Tool 设计

统一工具层（mcp-server 封装 business-mock REST）；统一信封、四权限闸门（身份/角色/客户归属/白名单）、write 必幂等+审批凭证、每工具独立熔断、只读缓存+事件失效。

| 工具 | 说明 | 只读 | 确认 | timeout |
|---|---|---|---|---|
| search_customers | 按姓名/标签/阶段检索客户 | 是 | 否 | 1500ms |
| get_customer_profile | 画像+元数据 | 是 | 否 | 1000ms，缓存 10min |
| list_follow_ups | 跟进记录分页 | 是 | 否 | 1500ms |
| list_purchases | 消费记录（Mock 微信小店） | 是 | 否 | 1500ms |

| create_schedule | 日程创建 | **否** | **是** | 2000ms，幂等键 |

错误码沿用冻结规范（E_VALIDATION/E_FORBIDDEN/E_TIMEOUT/E_UPSTREAM/E_CIRCUIT_OPEN/E_APPROVAL_REQUIRED/E_IDEMPOTENT_REPLAY + 域内码 C_NOT_FOUND、C_NO_ENOUGH_RECORDS 等）。

## 12. RAG 设计

| 集合 | 内容 | 服务对象 |
|---|---|---|
| playbook_kb | 话术库、异议处理手册、跟进 SOP、标签判定规则 | Coach / Ops |
| product_kb | 产品知识（零售商品目录、卖点、参数） | Coach（话术涉及产品时） |

纪律不变：叙述性知识走 RAG 且强制引用；客户事实（跟进/消费/画像）一律走 MCP；无命中诚实标注"通用建议"，不冒充库内话术。
分域检索：chunk 元数据带 `domain` 字段（product / sales / technical / policy），Query Rewrite 按意图注入 domain 过滤；保持 2 集合纪律，不为分域拆集合。
流水线：Query Rewrite（注入客户上下文）→ dense+sparse 混合各 top20 → RRF → Rerank（默认 LLM listwise，不部署独立 reranker）→ 阈值（≥0.60 直用 / 0.35~0.60 限定语 / <0.25 弃）→ ≤5 chunks 注入 → 引用落 message.citations。
更新与版本：active 版本指针原子切换、可回滚、引用可追溯。

## 13. Memory 设计（本项目中升格为核心）

| 层 | 存储 | 内容 |
|---|---|---|
| 会话短期 | Redis | 员工与 AI 最近 N 轮 + 当前客户上下文槽位，TTL 24h |

## 16. E2E Evaluation 设计

| 数据集 | 规模与构成 | 对象 | 指标与目标 |
|---|---|---|---|
| intent_eval | 200 条（种子 100 + LLM 扩写 100） | 三路意图融合 | L1 准确率 ≥92% |
| profile_eval | 20 客户×核心字段 | Profile Agent | 字段覆盖率 ≥90%、字段级准确率（对标人工标注集） |
| tag_eval | 120 条 | Ops Agent 打标 | 标签准确率、人工修正率（目标 ≤15%） |
| signal_eval | 80 条跟进记录 | 信号识别 | 四分类 P/R/F1，承诺类召回 ≥85% |
| talk_eval | 60 场景 | Coach Agent + RAG 检索 | 检索 Recall@5 ≥90%；四维 Judge（相关性/准确性/完整性/有用性）≥4.3/5；事实一致性（与画像冲突检测）；采纳率（上线后真实行为） |
| e2e_task_eval | 40 场景 | 全链路 | 任务完成率（提案已出/依据齐全/确认流程走通）、平均轮次 |

测试集构成（共 500 条）：**种子金标 ~200**（种子数据阶段产出）+ **LLM 扩写 ~200**（人工抽检）+ **员工行为回流**（上线后增量），形成"使用越多、评测越准"的飞轮。工程指标：MCP 工具成功率 ≥97%（tool_call_log 聚合，非抽样）。

特色机制：**员工行为即标注**——采纳/修改/拒绝/标签修正自动沉淀为评测样本（每周增量入库）。其余机制（eval_mode、Judge 分离、基线回归、预算护栏）沿用冻结规范。目标基线先于实验固化，简历只写实测值。

## 17. 异常场景

| # | 场景 | 系统行为 | 用户可见 |
|---|---|---|---|
| E1 | LLM 超时/不可用 | Gateway 重试 1 次→备用模型→失败则降级话术，Run=failed | "生成暂时不可用，请稍后重试" |
| E2 | 意图置信度低 | 澄清候选；<0.4 兜底+unknown 入池 | 选项卡澄清 |
| E3 | MCP/业务后端不可用 | 重试 1 次→结构化错误，禁止编造客户数据 | 明确告知读取失败 |
| E4 | RAG 无命中 | 标注"通用建议"，不冒充库内话术 | 建议卡带来源标识 |
| E5 | Milvus 不可用 | 相似客户功能置灰；画像/标签流程不受影响（结构化路径独立） | 功能降级提示 |
| E6 | Redis 不可用 | 会话退化为单轮模式，短期记忆停写 | 提示上下文可能丢失 |
| E7 | SSE 断线 | 自动重连+按 run_id 补齐 | 重连横幅 |
| E8 | 提案超时（30min） | 过期置 expired，可一键重新发起 | 灰显"已过期" |
| E9 | 并发/重复确认 | 幂等键+状态机拦截 | "该提案已处理" |
| E10 | 画像抽取与既有字段冲突 | 双值并呈员工裁决，不静默覆盖 | 冲突标记+依据对照 |
| E11 | 话术与客户事实冲突 | 生成后自检拦截重写 1 次，仍失败降级为要点式建议 | 标注"请人工核对" |
| E12 | 无凭证 write | MCP 拒绝+安全事件 | 不可见（兜底） |
| E13 | 记录不足强行分析 | 拦截，提示"跟进记录不足 3 条"并展示首访采集清单 | 冷启动引导 |
| E14 | 提示词注入诱导跨客户提问 | 客户槽位锁定 + prompt 约束"仅可讨论{当前客户}"，跨客户请求澄清/拒绝；MCP 归属校验兜底 | 澄清话术 |

## 19. 范围划分

**A. MVP**：business-mock 数据域 + sagt_agent 核心（三路意图、Orchestrator/Profile/Coach、HITL、Monitor 简版）+ sidebar（对话工作台/客户详情/画像/标签/话术）+ admin（员工管理/客户管理/会话监控）+ playbook_kb/product_kb + 评测 CLI（3 数据集）。

**B. P2**：Ops Agent 全套（信号识别+日程）、相似客户检索、拜访准备编排、质量报表、服务记录/订单管理页、Monitor 瀑布图、人工行为信号回流。

**C. ADV**：技能管理全套、评测平台化、批量任务调度、sagt_client SDK 正式发布形态、流失预警看板。

**D. 不做**：真实微信/企微接入、真实支付订单、多租户、员工 App、客户直接对话入口、模型微调。

## 20. 技术架构要点（对齐 SAGT 架构说明）

1. **模块化**：sagt_agent / sagt_admin / sagt_sidebar / business-mock / mcp-server / sagt_client(SDK) 独立部署，契约先行；
2. **智能体记忆**：LangGraph 承载状态机与 checkpoint（中断确认后恢复执行），Redis 短期 + MySQL/Milvus 长期双层记忆；
3. **API 封装**：sagt_client 以 OpenAPI + SDK 提供统一访问与记忆维护接口，未来对接真实生态只换实现不换契约；
4. **人工在环**：关键写操作全部 interrupt 确认，员工行为自动成为评测信号。

技术栈：React（双端 SPA）/ Java 21 + Spring Boot（business-mock）/ Python 3.11 + FastAPI + LangGraph（sagt_agent、mcp-server）/ MySQL 8 / Redis / Milvus / LLM Gateway / MCP / Docker Compose。
